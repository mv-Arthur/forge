# Отчёт консистентности документации редизайна ncottage

Метод: кросс-аудит 5 агентов (модель↔prisma, покрытие бэклога, вайрфреймы↔данные, логические
дыры/edge-cases, открытые вопросы/противоречия). Охват: `REDESIGN-TZ.md`, `PRISMA-DRAFT.md`,
`BUILD-BACKLOG.md`, `WIREFRAMES.md`, `TZ-VERIFICATION.md`, `HARVEST-REPORT.md`, `CONTENT-CHECKLIST.md`,
`CUSTOMER-BRIEF.md`. Дата: 2026-07-05.

## TL;DR — корневая причина

Независимая доработка (**PRISMA-DRAFT §1.10 + HARVEST-REPORT**) ратифицировала **«вариант A»**:
каталог **163 дома** (миграция из legacy), новая nested-модель **`ProjectMaterialVariant`** (материал =
своя цена + свои пакеты, `ProjectPackage` переезжает под вариант, `Project.price` = денорм min), а
technology/style/features/objectType/workType → **CMS-справочник `Taxonomy`** (не enum/const).

Но **`REDESIGN-TZ §1`, `WIREFRAMES`, `CUSTOMER-BRIEF`, `CONTENT-CHECKLIST` остались на старой модели**
(8 проектов, `ProjectPackage` под `Project`, enum-стили, единичный technology/price). При этом сам ТЗ
в шапке объявлен «источником истины при расхождении» — хотя фактически это **самый устаревший** документ.

→ **Перед WP0 нужна реконсиляция: подтянуть `REDESIGN-TZ §1/§5` вверх до варианта A, затем пробросить
вниз.** ~половина HIGH-находок схлопывается в это одно действие.

## HIGH — блокеры (свести до старта WP0)

- **H1. Модель материалов не в ТЗ.** `ProjectMaterialVariant`/перенос packages/денорм price (PRISMA §1.10,
  HARVEST «решено A») ОТСУТСТВУЮТ в `REDESIGN-TZ §1.1/§1.2/§1.5/§1.6` — там packages/price на самом
  Project. Три дока описывают взаимоисключающие модели. → внести вариант A в ТЗ §1.
- **H2. Taxonomy vs enum.** ТЗ §1.6 «расширить PROJECT_STYLES/PROJECT_FEATURES (const/enum)» ↔ PRISMA
  §1.10 + BACKLOG WP2-T8 «CMS-справочник Taxonomy». Двойной источник подписей. → ТЗ на Taxonomy.
- **H3. Масштаб каталога 8 vs 163.** ТЗ §А/§5, WIREFRAMES («Найдено 8 проектов»), BACKLOG WP7 («packages
  8/8», риск №2 «1/8») ↔ HARVEST/WP9 «163 дома». Расхождение ×20, причём внутри одного BUILD-BACKLOG
  (WP7=8 vs WP9=163). → зафиксировать «8 демо сейчас → 163 после публикации», описать состояние
  каталога после импорта (163 draft), заменить хардкод «8» в вайрфреймах на «N».
- **H4. Имена связей: `baseProjectSlug` vs `baseProjectId`.** ТЗ §1.3/§1.5 зовут поле `baseProjectSlug`,
  а §1.6/PRISMA — `baseProjectId` (FK→id). Аналогично `reviewId`(БД) ↔ `reviewSlug`(контракт) — нигде не
  оговорено «id внутри / slug наружу». → привести §1.3/§1.5 к `baseProjectId`, задокументировать
  сериализацию в slug.
- **H5. `Review.builtObjectId` — ошибка.** ТЗ §1.6 требует добавить скаляр `Review.builtObjectId`; PRISMA
  доказательно отвергает (создаёт конкурирующую вторую relation → Prisma-ошибка). Связь только через
  `BuiltObject.reviewId`. → переписать ТЗ §1.6.
- **H6. Выбор материала = «вилка цены»: два несовместимых механизма в вайрфреймах.** WIREFRAMES
  одновременно рисует (а) блок «тот же дом в другом материале» через `ProjectRelation.kind=other-material`
  (отдельные Project) и (б) inline «селектор материала (вилка цены)». Вариант A заменяет это единой
  моделью вариантов. → выбрать вариант A, удалить блок other-material + `ProjectRelation.kind='other-material'`.
- **H7. Фолбэк цены не задан.** Проект с 0 пакетов / `price=NULL` при варианте A — что показывает карточка
  и sticky (калькулятор скрыт, но «под ключ от N ₽»? «Стоимость по запросу»?). Пустое состояние не
  специфицировано. → описать фолбэк цены.
- **H8. Поле `projectType` (серийный/индивидуальный) отсутствует.** WIREFRAMES ветвит лейаут и рисует бейдж
  типа по несуществующему полю (§Д#10). → либо завести `projectType`/`priceMode`, либо явно зафиксировать
  scope-cut «только серийный».
- **H9. `likesCount` без источника.** Вайрфреймы каталога рисуют «лайки-счётчик», в модели поля нет. →
  добавить `Project.likesCount` (CMS-редактируемое «соц-число») либо убрать элемент.
- **H10. Устаревшая шапка ТЗ.** v2-нотис: «594 страниц» (реально ~1137 / 912 project) и ветка
  `feat/ncottage-cms` (влита в main). → обновить шапку, убрать имя ветки.
- **H11. TZ-VERIFICATION не пропагирован в ТЗ.** 9 числовых коррекций §А не внесены, хотя ТЗ сам объявил
  «v2 приоритетна»: цена 8.0/14.5→**8.2/15.4** (n=333), комплектаций 192/250→**333/333**, aps фото ~33→~24,
  §Д#3 «8-800 у aps да» ↔ верификация **aps 8-800 = 0/157** (самопротиворечие), gwd Telegram 100% (не «нет»).
- **H12. CUSTOMER-BRIEF/CONTENT-CHECKLIST на «8 проектов».** Просят у заказчика «цены/фото по всем 8» —
  противоречит варианту A (163 дома) и 333 legacy-карточкам. Заказчику выставлен неверный запрос. →
  переформулировать под миграцию/163.

## MED

- **M1.** `reviewId`(модель) ↔ `reviewSlug`(shared-контракт) — рассинхрон имён без оговорки (§1.3 vs §4.3).
- **M2.** `roomCounts` (новое поле ТЗ §1.1) не заведён в PRISMA (нет nested-модели/JSON). → добавить `ProjectRoomCount`.
- **M3.** Схема `Setting` не описана в §1, хотя вайрфреймы тянут из неё ~10 значений (8-800, мессенджеры,
  ставка ипотеки, 4 KPI-счётчика, ID Метрики, гарантия). → завести схему `Setting`/`CompanyStats` в §1.4/§1.6.
- **M4.** `floors`: модель select `1/2/мансарда` + `floorsIn Int[]`, вайрфрейм-фильтр `1/1.5/2/манс`
  (1.5 не влезает в Int; мансарда дублируется в floors и features). → enum `{1,1.5,2,mansard}`, `floorsIn` = массив enum.
- **M5.** DoD WP4-T3 «все оси §Г» ↔ SelectionFilter покрывает ~половину (нет формы дома/типа крыши/размера
  пятна/особенностей). → сузить DoD или расширить фильтр.
- **M6.** Byte-identity §6 PRISMA написан БЕЗ учёта варианта A (перенос packages → не аддитивно, не
  byte-safe). → дописать подраздел про вариант A.
- **M7.** FK `baseProject` SetNull → осиротевшая CTA «Хочу такой дом» (empty-state не задан).
- **M8.** Объект без координат → карта (выпадает из синхро-ленты? мини-карта на детальной?). Empty-state не задан.
- **M9.** Объект без `heroMedia` → обложка; при этом shared `image:string` обязателен, а `heroMediaId` nullable
  — конфликт типов + empty-state.
- **M10.** `technology/objectType` NULL на 12 объектах (backfill опциональный) → молча исчезают при активном
  фильтре §2.4. → обязательный backfill или бакет «Не указано».
- **M11.** `BuiltObjectMilestone` — модель есть (WP0-T9), UI-рендера вех на /works/[slug] в бэклоге нет.
- **M12.** email-подписка — `LeadSource='subscribe'` заведён, UI-задачи в WP6 нет (контракт без потребителя).
- **M13.** Бейдж «N фото» — derived (`COUNT(BuiltObjectPhoto)`), нигде не оговорён; риск «1» на всех до WP7-контента.
  → скрывать при N≤1.
- **M14.** `bedrooms` gwd: в JSON-LD нет «Спальни» (только «Комнаты») → при миграции пусто. → правило деривации.
- **M15.** tour3d понижен в §Д#4, но в §1.1/§2.3/§2.5/WIREFRAMES подан как штатная секция без пометки «опц.».

## LOW

- **L2.** Сортировка «по популярности» — нет сортируемого поля (пересекается с likesCount).
- **L3.** Сортировка «по дате» на /works — даты опциональны → недетерминированный порядок (null). → fallback-ключ.
- **L4.** Два шаблона gwd (§Д#10) — scope-cut не задокументирован.

## Открытые вопросы (для заказчика / решения)

- **Карта: Leaflet+OSM (дефолт) vs Яндекс.Карты** — не подтверждено; для RU/SEO Яндекс часто предпочтителен. Спросить.
- **`Settlement`/участки** — «продаёте ли дома с участком/посёлки?» Скрытая зависимость, не эскалирована в чек-лист.
- **Гарантия** — актуальный срок (не тащить хардкод «7 лет» в прод).
- **Квиз: 6 шагов** (зафиксировать, убрать вилку «5-6»).
- **`projectType`** — заводим индивидуальные проекты или scope-cut «только серийный»?

   packages + масштаб 163. ТЗ ← PRISMA/HARVEST (H1, H2, H3). Снимает ~половину HIGH.

4. **Синхронизировать CUSTOMER-BRIEF/CONTENT-CHECKLIST** на 163/миграцию + добавить гарантию/карту/участки в

5. **Досоздать модельные опоры**: `ProjectRoomCount`, схема `Setting`, `projectType`, `likesCount`, enum `floors`
