# Kickoff-промпт для реализации ncottage CMS

Скопировать целиком в новую сессию Claude Code (запущенную в корне репозитория
`forge`). Промпт самодостаточен: опирается на согласованные ТЗ и план.

---

ultracode

Реализуем ncottage CMS «под ключ» по уже согласованным ТЗ и плану. Работай в
режиме ultracode: на объёмных фазах разворачивай многоагентные workflows
(параллельный разбор/миграция контента, состязательная верификация ревью), на
мелких механических правках — обычный режим. Приоритеты: скорость, эффективность,
качество — без срезания углов на проверках.

## Что прочитать перед стартом (обязательно, именно в этом порядке)

1. `docs/ncottage-cms/SPEC.md` — техзадание: цели, архитектура, модель данных,
   принятые решения D1–D7, контент-модель, требования к админке.
2. `docs/ncottage-cms/ROADMAP.md` — эпики A–G и порядок PR с зависимостями и DoD.
3. Память проекта (`project_ncottage_backend`, `feedback_forge_workflow`,
   `project_forge_overview`, `project_ncottage_types_react_dedupe`) — подтянется
   автоматически; учитывай её.

Решения D1–D7 согласованы — заново их не переоткрывай. Кратко: S3/MinIO для медиа,
доставка лидов Telegram+email, UI Tailwind+shadcn, полная нормализация проекта,
весь контент поэтапно, мультиюзер+роли (RBAC admin/editor), on-demand ISR.

## Порядок исполнения

Идём строго по ROADMAP. Старт — эпик **A1** (Tailwind + shadcn в `ncottage-admin`),
затем A2/A3. Дальше A/B/C/D/G параллелизуемы после A3/B1; контент (E) — после E0.
Это многосессионная работа: **в начале каждого захода** сверься с `git log` и
ROADMAP — что уже сделано в ветке, чтобы не дублировать.

## Модель поставки (важно)

Вся работа ведётся в **одной feature-ветке** (создать от `main`, напр.
`feat/ncottage-cms`) и закрывается **одним PR в самом конце**, который мержит
владелец. Промежуточных PR нет — владелец не хочет постоянно заходить и аппрувить.

- Эпики/шаги ROADMAP — это **этапы и коммиты внутри одной ветки**, не отдельные PR.
- Коммить осмысленными порциями по шагам ROADMAP (читаемая история, откатываемые
  куски), но PR открывай только в конце (или когда владелец явно попросит).
- Промежуточного ревью не будет — **качество держится на твоей самопроверке**.
  На каждом крупном этапе перед коммитом: e2e backend, визуальный аудит фронта,
  а в ultracode — состязательная верификация (агенты-скептики) ключевых изменений.
- Дёргай владельца по ходу только: (1) когда нужны внешние креды (Telegram/SMTP/
  S3); (2) на редких продуктовых развилках с высокой ценой ошибки. Остальное —
  разумный дефолт, упомяни и продолжай.

## Definition of Done на каждый этап (перед коммитом этапа)

- `pnpm -r typecheck`, `pnpm lint`, `pnpm -r build` зелёные — ветка всегда рабочая,
  чтобы итоговый PR прошёл CI без сюрпризов.
- `@forge/shared` собран перед потребителями (топологически); новые доменные типы и
  словари — только в `@forge/shared`, не дублировать.
- Backend-изменения проверены e2e против живой БД (см. инфру ниже).
- Изменения публичного сайта — по DoD ncottage-www из памяти (full-page визуальный
  аудит, не только DOM-снапшот).
- Миграции Prisma обратимы; `seed`/`seed-data` обновлены под новую модель.
- Заголовок итогового PR — в формате, который требует CI. Нигде (PR/commits/
  комментарии) не упоминать Claude/агента.

## Критичные технические тонкости (не наступить повторно)

- **`.js` в импортах:** в `ncottage-api` и `@forge/shared` относительные импорты
  идут с `.js` (ESM-стиль). В Next-приложениях (`ncottage-admin`, `ncottage-www`)
  — **без** `.js` (ломает webpack-резолв).
- **`@types/react` dedupe:** в Next-приложениях не ломать tsconfig paths-маппинг
  `react`/`react-dom` (чинит дубль `@types/react@18` от styled-jsx). При добавлении
  зависимостей следить за этим — особенно при установке Tailwind/shadcn.
- **`@forge/*` в api:** в `ncottage-api/tsconfig` `paths:{}` намеренно отменяет
  унаследованный `@forge/*` (иначе SWC инлайнит путь в require → рантайм падает).
- **shared в www:** потребляется через node_modules (typecheck=src через
  `exports.types`, build=dist). `transpilePackages`/tsconfig-path на src ломают
  Next-резолв — не использовать.
- **Зависимости** не ставить молча — если нужна новая, сначала обозначь (но
  Tailwind/shadcn/react-hook-form/zod/TanStack Table/zod уже одобрены планом).

## Инфраструктура (локально)

- Postgres в Docker: `docker-compose -f apps/ncottage-api/docker-compose.yml up -d`
  (движок colima: `colima start`; использовать standalone `docker-compose`, не
  плагин `docker compose`). Для эпика B добавить MinIO в этот compose.
- `.env` сервисов gitignored; локальный админ — `admin@ncottage.local`. Реальные
  креды внешних сервисов (Telegram bot token/chat_id, SMTP, S3-ключи) запрашивай у
  меня, когда дойдёшь до эпиков B/D — локально поднимай MinIO и mock-доставку.

## Как вести работу

- Перед крупным эпиком — короткий план (ключевые файлы, миграции, риски), затем
  исполняй. Не переспрашивай по уже решённому в SPEC.
- Точечные развилки внутри эпика (дробление E2 по секциям, тема/акцент админки в
  A2, набор полей при нормализации конкретной контент-сущности) — решай разумным
  дефолтом и упомяни, либо спроси одним сжатым вопросом, если цена ошибки высока.
- Держи меня в курсе по завершении каждого PR/эпика: что сделано, что проверено,
  что дальше.

Начни с чтения SPEC.md и ROADMAP.md, свери текущее состояние репозитория, затем
приступай к A1.
