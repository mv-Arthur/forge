# ROADMAP: ncottage CMS

План реализации [SPEC.md](./SPEC.md) по этапам и PR. Порядок учитывает зависимости:
ядро (медиа → проекты → лиды) идёт раньше контент-CMS; админка-фундамент — самый
первый, т.к. на нём строятся все редакторы.

Модель поставки (согласовано): вся работа ведётся в **одной feature-ветке** и
закрывается **одним PR в конце**, который мержит владелец. Промежуточных PR нет —
эпики ниже это **этапы внутри одной ветки**, а не отдельные PR.

Принципы:
- Эпики/шаги ниже — структура коммитов, а не PR. Коммитить осмысленными порциями
  по шагам ROADMAP (чтобы история читалась и кусок можно было откатить), но PR один.
- На каждом этапе держать ветку в рабочем состоянии: `typecheck`/`lint`/`build`
  зелёные, чтобы итоговый PR прошёл CI без сюрпризов.
- Backend сущности делать и проверять e2e **до** её admin-UI (внутри той же ветки)
  — порядок коммитов, не PR.
- Поскольку промежуточного ревью нет, качество держится на самопроверке:
  обязательны e2e backend, визуальный аудит фронта (DoD www), а в ultracode —
  состязательная верификация ревью перед коммитом крупного этапа.
- Заголовок итогового PR — в формате, который требует CI. Без упоминания агента в
  PR/коммитах.
- Контент-CMS (эпик E) идёт после ядра и не блокирует его.

Легенда зависимостей: `→` «после».

## Эпик A. Фундамент админки (UI-кит)

База для всех редакторов. Без изменений в backend.

- **A1. Tailwind + shadcn/ui в `ncottage-admin`.**
  Подключить Tailwind, инициализировать shadcn, базовые примитивы (Button, Input,
  Select, Dialog, Toast, Table, Tabs, Card, Form). Учесть `@types/react` dedupe.
  DoD: примитивы рендерятся, `typecheck`/`build` зелёные, старые страницы не сломаны.

- **A2. Каркас: layout + навигация + редизайн логина.** → A1
  Боковая навигация (Проекты/Медиа/Лиды/Контент), топбар (админ + выход), крошки,
  состояния loading/empty/error, тосты. Перенести login на дизайн-систему.
  DoD: навигация по разделам, единый layout, логин в новом стиле.

- **A3. Паттерн форм и таблиц.** → A1
  Обёртки: `DataTable` (TanStack, поиск/фильтр/пагинация), `Form`-инфраструктура
  (react-hook-form + zod), `RepeaterField` (useFieldArray + dnd-сортировка).
  Перевести существующий список/форму проектов на новые обёртки (без сырого JSON
  для вложенного — временно с локальной zod-схемой до нормализации в C).
  DoD: проекты редактируются через repeater-поля; JSON-textarea убраны.

## Эпик B. Медиа-библиотека

- **B1. Backend: хранилище + Media API.** (D1)
  MinIO в docker-compose; модуль `media`; `POST/GET/DELETE /media`; метаданные в
  БД; извлечение размеров изображений; env-валидация S3.
  DoD: e2e загрузка/листинг/удаление против MinIO; типы `Media` в `@forge/shared`.

- **B2. Admin: библиотека + `MediaPicker`.** → A3, B1
  Раздел «Медиа» (грид с превью, загрузка drag&drop, удаление), компонент
  `MediaPicker` (выбор/загрузка, множественный выбор + сортировка для галерей).
  DoD: можно загрузить файл и выбрать его в форме; превью работают.

## Эпик C. Проекты (нормализация)

- **C1. Backend: нормализация модели + миграция данных.** (D4) → B1
  Prisma-схема (ProjectImage/FloorPlan(+Room)/Package(+Include)/Option/Relation),
  миграция + скрипт переноса JSON→таблицы, переписать `ProjectsService`
  (toDomain/create/update на вложенные записи), обновить `seed`. Контракт `Project`
  в `@forge/shared` сохраняет форму ответа для www (агрегируем в сервисе).
  DoD: e2e CRUD проектов на новой модели; www читает без изменений API-ответа;
  миграция данных проверена.

- **C2. Admin: редактор проекта на нормализованной модели + медиа.** → A3, B2, C1
  Форма проекта с repeater-полями (планировки с комнатами, пакеты с включениями,
  опции, галерея через `MediaPicker`, связанные проекты — выбор из списка).
  DoD: проект создаётся/правится целиком через UI, без JSON-полей; превью медиа.

## Эпик D. Лиды

- **D1. Backend: доставка (Telegram + email) + redeliver.** (D2)
  `CompositeLeadDelivery`, `TelegramLeadDelivery`, `EmailLeadDelivery`,
  `POST /leads/:id/redeliver`, `deliveryAttempts`, env-валидация провайдеров,
  изоляция ошибок доставки от создания лида.
  DoD: лид доставляется в Telegram/email; ошибка пишется в `deliveryError`;
  повторная отправка работает; unit на композитную доставку.

- **D2. Admin: список лидов с фильтрами/статусами/деталями.** → A3, D1
  DataTable (фильтр по источнику/статусу/дате, поиск), карточка лида, смена
  статуса, кнопка «доставить повторно», индикатор статуса доставки.
  DoD: лиды просматриваются и обрабатываются удобно; виден статус доставки.

## Эпик E. Контент-CMS (фазируется по приоритету, D5)

Каждая фаза: backend (модель + API + сид-импорт из текущих `*.ts`/`json`) →
admin (список/форма) → интеграция www (чтение из API + ISR-ревалидация).
Зависит от A (фундамент), B (медиа), и §5.5/D7 (revalidate).

- **E0. Revalidate-механизм.** (D7) → C1
  `/api/revalidate` в `ncottage-www` (секрет, по тегам/путям) + вызов из API/admin
  после мутаций. База для всех контент-фаз.

- **E1. Настройки: навигация, футер, контакты.** (§6.1) → A2, E0
  Singletons; www читает из API. Высокая отдача, низкий объём.

- **E2. Главная страница (секции).** (§6.3) → B2, E0, E1
  Page + типизированные секции (hero, advantages, stages, geography, reviews,
  featured, guarantees, faq, contact). Самая объёмная фаза — можно дробить по
  секциям на под-PR.

- **E3. Блог.** → B2, E0
  Article (slug, разделы, highlights, checklist, related, SEO), редактор статей,
  импорт 8 существующих статей.

- **E4. Услуги + SEO.** → B2, E0
  Service (30+ полей, сценарии) + SEO-контент; самая сложная коллекция — возможно
  частичная нормализация + структурированный JSON для редких полей.

- **E5. Прочие коллекции.** → B2, E0
  Акции, отзывы, вакансии, FAQ, построенные объекты, сертификаты, партнёры.
  Финансовые лендинги (FinanceLanding) и юр. страницы — по остаточному принципу
  (или оставить в коде, см. D5).

## Эпик G. Доступ и роли (RBAC, D6)

- **G1. Backend: роли + управление пользователями.** → (рядом с A, до admin-разделов
  с удалением)
  `role` в модели `Admin` (`admin`/`editor`), `RolesGuard` + декоратор `@Roles`,
  CRUD пользователей (`/admins`: list/create/update-role/reset-password/delete,
  только `admin`), первый суперюзер через сид/env. Миграция существующей учётки в
  `admin`.
  DoD: e2e — `editor` не может удалять/управлять юзерами (403), `admin` может;
  тип `Role` в `@forge/shared`.

- **G2. Admin: раздел «Пользователи» + скрытие действий по роли.** → A3, G1
  Список/создание/удаление учёток, смена роли, сброс пароля (видно только `admin`).
  Скрывать в UI недоступные роли действия (удаление, управление юзерами).
  DoD: редактор не видит запретных действий; админ управляет пользователями.

## Эпик F. Сквозное (по мере необходимости)

- **F1. SEO-поля по всем публичным сущностям** — `generateMetadata` из API.
- **F2. Аудит фронта** после каждой контент-фазы (full-page, по DoD www).
