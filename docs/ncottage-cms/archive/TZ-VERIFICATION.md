# Верификация ТЗ по корпусу (B4 + C6, финал трека C)

Детерминированная сверка `docs/ncottage-cms/REDESIGN-TZ.md` (v2, Приложение) с харвест-корпусом
`research/.corpus/`. Источник чисел — `research/.corpus/_fields.json` (сгенерирован
`.scratch/c-verify/extract.cjs`) и `research/.corpus/_summary.json`. ТЗ не редактировался;
фактические ошибки собраны в разделе «Предлагаемые коррекции REDESIGN-TZ.md».

**Статус финализации:** независимый верификатор дал `overallOk = true` (аналитические выводы ТЗ
верны). Внесены три подтверждённых числовых/учётных исправления к самой этой сверке (легаси-built
медиана, учёт файлов gwd, приоритет источника цены) и добавлена положительная верификация таксономии
§Г. Все правки перепроверены собственным скриптом по сырому корпусу (ниже — «переверификация»).

**Легенда confidence:** `high` — JSON-LD (structured) / точный count / breadcrumb; `medium` —
регэксп по отрендеренному `fullText`; `low` — порядок-зависимая эвристика.

**Ключевая методологическая находка (влияет на все проценты presence):** из 596 legacy-страниц
типа `project` только **333 — настоящие карточки дома** (несут `Product` JSON-LD с
`AggregateOffer`). Остальные 263 — это отфильтрованные листинги-категории (3-сегментный URL, но в
`fullText` много карточек и чипы фильтров, без единого `Product`). Поэтому FEATURE/CTA-проценты по
legacy, посчитанные по всем 596, **разбавлены** и занижены (например `materialChoice`/`packages` =
56% по 596, но **100% по 333 настоящим карточкам**). Авторитетны структурированные счётчики по 333,
не presence%. Независимо подтверждено: legacy Product=333, AggregateOffer=333, offerCount у всех = 3.

**Известный дефект агрегаторов (даёт кривые числа, не выводы):** helper `median()` в обоих
агрегаторах для чётного `n` берёт **верхний** центральный элемент `s[n/2]` вместо среднего двух
центральных. Задел только там, где два центральных элемента различаются — это **legacy built
imageCount** (n=40: 153 вместо 149). Легаси-project median 80 (n=596) не задет: оба центральных
элемента (idx297, idx298) = 80. Значение `built = 153` в `_fields.json`/`_summary.json` и во всех
производных строках ниже помечено как некорректное; верное — **149** (см. коррекцию #2).

  структурированы (нет per-project style-поля) — это провал в данных, не в §Г. §Г принимается как

## Переверификация (независимый скрипт по сырому корпусу)

Все спорные числа перепроверены заново `node`-скриптом прямо по `research/.corpus/*/*.json` (не через
агрегаторы), чтобы отделить артефакты `median()` от данных.

1. **legacy built imageCount, n=40**, sorted =
   `27,36,47,66,71,73,74,80,84,87,93,104,109,111,112,121,131,138,142,145,153,154,157,158,163,166,182,191,192,196,198,202,206,213,218,219,234,252,361,417`.
   Центральная пара — idx19=**145**, idx20=**153**. Корректная чётная медиана = (145+153)/2 = **149**.
   Хранимая `153` = `s[floor(n/2)]` (верхний элемент, баг). `_fields.json` builtImageCount.dist.median
   и `_summary.json legacy.builtImages.median` оба = 153 → **исправить на 149**.
2. **legacy project imageCount, n=596**: idx297=80, idx298=80 → корректная медиана = **80**. Баг
   чётной медианы не влияет (оба центральных совпадают). Значение **верно, не трогать**.
3. **legacy цена (JSON-LD, n=333)**: lowPrice median = **8 227 200** (8.23 млн), highPrice median =
   **15 371 005** (15.37 млн) — воспроизведено байт-в-байт из `AggregateOffer`. `_summary` text-regex
   (n=595) даёт 7.49/11.51 млн по замусоренному множеству листингов — **не авторитетно**.
4. **gwd файлы**: на диске 185 (159 project + 26 built); 2 built (`built__built-drawList-php.json`,
   `built__built-drawSection-php.json`) — php-экспорт с imageCount=0, молча отброшены → агрегаторы
   пишут total=183, built=24. Разница задокументирована; на выводы не влияет.
5. **§Г Технологии**: 15 маркеров, 14 из них на 596/596, «стеклянные стены» как точная фраза = 0
   (ярлык рендерится иначе) — что и есть предупреждение о точности ярлыков. Блок — universal chrome.

## Предлагаемые коррекции REDESIGN-TZ.md (финальный список)

Формат: **якорь → старое → новое + доказательство.** Только фактические ошибки/уточнения; сам ТЗ не
редактировался (применит человек после ревью). Отсортировано: сначала числовая ошибка, затем
уточнения.

1. **§А, строка 356 «Цена под ключ (медиана low/high) | 8.0 / 14.5 млн ₽»**
   → заменить на **«≈8.2 / 15.4 млн ₽ (JSON-LD AggregateOffer, n=333)»**.
   *Уточнение (не ошибка):* low близко, high занижен на ~0.9 млн.
   Доказательство: `_fields.json legacy.priceLow.dist.median=8227200`,
   `priceHigh.dist.median=15371005`; воспроизведено скриптом. **НЕ** брать `_summary` text-regex
   7.49/11.51 (n=595, замусорено листингами).

2. **Только для этой сверки (не для ТЗ) — числовая ошибка агрегаторов: legacy built imageCount
   «медиана 153» → «медиана 149».**
   Якоря источника: `_fields.json` строка ~196 (`legacy…builtImageCount.dist.median`),
   `_summary.json legacy.builtImages.median`. Ошибка — баг чётной медианы (взят верхний центральный
   153 вместо среднего 145 и 153). Верное = **149**. Доказательство: n=40, центральная пара 145/153,
   (145+153)/2=149 (см. Переверификацию п.1). Вывод §Д#7/§В ТЗ «десятки–~130, медиана раздута» —
   **верен и без правки** (ТЗ и так отвергает раздутую медиану); менять само ТЗ не требуется, но
   ссылаться на «153» нельзя. Заодно починить `median()` (для чётного n усреднять два центральных) и
   перепроверить прочие чётные медианы (project=80 корректна).

3. **§А, строка 352 «Проектов в каталоге | ~568 (legacy)»** — *методологическое уточнение (не
   ошибка).* 568 = размер URL-множества; **детальных карточек дома с ценой = 333** (263 из 596 снятых
   project-URL — отфильтрованные листинги-категории без `Product`). Для планирования миграции контента
   (WP7) считать **333** legacy / **157** aps / **123** gwd реальных карточек, не sitemap-тоталы.
   Доказательство: inner-type count legacy 596 project / aps 157 / gwd 159; deep JSON-LD: legacy
   Product=333, gwd Product=123 (27 серийных + 96 индивидуальных), aps Product=0. Три источника
   (_fields, _summary, скрипт) сходятся на 596/157/159.

4. **§А, строка 353 «Реальных фото/проект | … aps ~33»** → **«~24 (медиана)»**.
   *Мягкое расхождение.* Медиана imageCount aps = 24 (min 10 / max 42 / mean 26); «~33» — ближе к
   среднему на богатых карточках. Доказательство: `_fields.json aps.imageCount.dist.median=24`.

5. **§А, строка 357 «Комплектаций | 3 (192/250)»** → **«3 (333/333 карточек с Product)»**.
   *Устаревший снимок.* «192/250» — историческое число; в текущем корпусе offerCount `={3}` у
   **333/333**, названия Базовая/Стандарт/Комфорт — единственная комбинация у 333/333.
   Доказательство: `legacy.offerCount.dist={"3":333}`, `packageLabels.combos={"Базовая/Стандарт/Комфорт":333}`.

6. **§А, строка 359 «8-800 | да (футер) [aps] | да (100%) [gwd]»** и **§Д#3 «8-800 присутствует у aps
   и gwd»** — *расхождение с корпусом.* В отрендеренном `fullText` aps 8-800 **не найден (0/157)**;
   подтверждён только у gwd (100%). Предлагаемая формулировка: «8-800 — только gwd (100%); у aps в
   снятом контенте не обнаружен — перепроверить футер вручную; legacy — нет».
   Доказательство: `aps.fields.ctaPresencePct.values.phone800=0`, `gwd…=100`.

7. **§А, строка 358 «Мессенджеры на карточке | … gwd: нет»** — *неточность.* У gwd Telegram
   присутствует **100%** (глобальные формы/футер), но не как per-card CTA. Предлагаемая формулировка:
   «gwd — Telegram/МАКС в глобальных формах (100%), но не на самой карточке».
   Доказательство: `gwd.ctaPresencePct.telegram=100`.

8. **§Б (gwd) и §1.1** — *уточнение источника «спальни» (не ошибка ТЗ).* В gwd JSON-LD
   `additionalProperty` есть Этажность/Площадь/**Комнаты**/Санузлы, но **нет «Спальни»** (0/123). При
   маппинге на нашу модель `bedrooms` для gwd-подобных данных выводить из «Комнаты» или парсить
   карточку, а не ожидать структурированное поле. Доказательство: `gwd.bedrooms.n=0`.

9. **§Г, «Размеры пятна (29)» (строка 422)** — *нюанс (не ошибка).* In-page сетка размеров варьирует
   по категории: {29:6, 31:124, 32:79} страниц; 29 — минимальная/базовая инстанциация, не
   универсальное число. Формулировка «≈29–32, база 29» точнее. Плюс *label-precision аннотация к §Г*:
   реальные заголовки сайдбара — «Технологии»/«Особенность»/«Размер»/«Стиль», не строки §Г; будущему
   верификатору матчить по фактическим заголовкам, иначе 0-совпадений читается как «таксономии нет».
   Доказательство: блок «Технологии» = 15 чипов на 596/596 (1 distinct-блок, chrome); dimension-grid
   count distribution {29:6, 31:124, 32:79}.
