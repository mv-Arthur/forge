# Выгрузка каталога из legacy (ncottage.ru) → нормализованные данные

Детерминированная выгрузка структурных данных каталога из харвест-корпуса `research/.corpus/legacy/`
в нормализованный вид под сиды WP7. Генератор: `research/normalize-legacy.cjs` (fs/path, без
зависимостей). Выходы: `research/.corpus/projects.normalized.json`,
`research/.corpus/built-objects.normalized.json`. Реальные сиды/схема НЕ трогаются.

## Что на входе и зачем

Текущий каталог сайта — **8 демо-проектов** (Норд/Аластер/…/Отто) с локальными плейсхолдер-картинками
`/public/images/projects/*.jpg` и generic-описаниями. Это не мигрированный контент, а заглушки со
сборки CMS. Из 8 имён на legacy реально существуют 5 (Норд/Аластер/Вальтер/Элиот/Отто), 3 (Фауст/Берг/
Карл) — выдуманные. Вместо привязки к демкам — выгружаем реальный каталог с legacy целиком.

## Фото — извлекаются контейнерным ре-харвестом (обновление, снимает прежний пессимизм)

Первая версия брала `images[]` из корпуса плоско (фото дома + карусель «похожих» + ассеты темы) — чистые
галереи регэкспом не отделялись (был вывод «не восстанавливаются»). **Решено ре-харвестом по DOM-контейнеру**
(`research/harvest-images.cjs`): своя галерея проекта = `.product-page__gallery-slider`, фотохроника объекта =
`.built-houses-item-page__content-gallery_slider-carousel`; карусель «похожие» (отдельный
`attachment-woocommerce_thumbnail`) не берётся → контаминация 0. Результат в `research/.corpus/images.json`,
подхватывается `normalize-legacy.cjs` в `normalized.json`:
- рендеры-галерея **98%** (160/163, 730 картинок), планы этажей **63%** (102/163, 178 планов);
- у остальных 37% домов плана на legacy НЕТ (ни картинки, ни PDF, проверено вживую) → дослать из проектных файлов заказчика;
- фотохроники объектов **100%** (40/40, ~66 фото/объект, 2645 фото).

Забор URL'ов в MinIO — WP1-T4/WP7. Legacy отдаёт веб-размер (проекты 1024×731); оригиналы качеством — от заказчика.

## Оговорки честности

- Цены legacy — **маркетинговые «Цена от»** (ниже базового пакета) и **снимок во времени**. `priceFrom`
  ниже `packages[0]` (Базовая) закономерно. Публиковать как есть нельзя — сверить актуальность с
  заказчиком (см. CONTENT-CHECKLIST). Базовый пакет — реальная нижняя граница.
- Группировка по (имя+габарит) может слегка расходиться на редких кейсах разного написания имени
  (163 vs 144 в первичной разведке); ошибки — единичные, влияют на 1-материальный хвост.
- Гостиницы/бани (19) — без габаритов в h1, вынесены в отдельный бакет; при желании досидить руками.

## Открытое модельное решение (вскрыто выгрузкой)

86 домов имеют один и тот же дизайн в 2–4 материалах, у каждого материала — своя цена и свои 3 пакета.
Как это моделить:

- **Вариант A — дом = 1 `Project` с вложенными материал-вариантами.** Новая nested-модель
  `ProjectMaterialVariant{technology, priceFrom, mortgageFrom, packages[]}`; `ProjectPackage` переезжает
  под вариант (пакеты у каждого материала свои). Каталог = **163 карточки**, на детальной — переключатель
  материала меняет цену/пакеты. Точно повторяет legacy-фичу «построить из» (§Д#2), чистый каталог.
  Цена: переструктурировать packages/price под вариант — правка PRISMA-DRAFT/WP0 (сейчас там этого нет).
- **Вариант B — каждый материал = отдельный `Project`, связка `ProjectRelation.kind="other-material"`.**
  **314 проектов**, текущая модель (пакеты на проекте) подходит без правок. Минус: каталог = 314
  near-дублей одного дома → нужна группировка/дедуп на листинге. Это то, что подразумевает ТЗ v1.

**РЕШЕНО (2026-07-05): вариант A.** Каталог 163 вместо 314 near-дублей, материал как атрибут одного дома,
UX как у legacy. Модель `ProjectMaterialVariant` (материал + цена + пакеты) зафиксирована в PRISMA-DRAFT
§1.10; `ProjectPackage` переезжает под вариант. Справочные поля (technology/style/features) — CMS-справочник
`Taxonomy` (не enum/const), сид из §Г; поведенческие (status/stage/kind) — const в коде.
