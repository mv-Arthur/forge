# Подбор дома: методология фильтров + спека квиза

> **Роль (для агента):** КАНОНИЧЕСКИЙ док по фильтрам каталога и квизу «Подбор» — методология,
> состав Primary/Secondary/Drop, спека квиза-гибрида. Реализуя фильтры/квиз — источник ЗДЕСЬ. Данные
> фильтров конкурентов — REDESIGN-TZ §Г; модель `Quiz` — PRISMA-DRAFT §1.11; задачи — BUILD-BACKLOG WP4-T3/WP6-T1.

Закрывает открытую design-задачу «Подбор» (§6.6 ТЗ). Один **общий словарь критериев** питает и
фильтры каталога, и шаги квиза (оба админимы из CMS). Всё заземлено на `research/.corpus/_fields.json`
(детерминированная выгрузка по 333 legacy-карточкам с ценой = наш будущий каталог 163) + таксономию
фильтров конкурентов (§Г) + что конкуренты выносят вперёд/прячут.

## 1. Методология: включать фильтр, если проходит 5 проверок

1. **Заполненность данных** — поле есть в модели И заполнено у ≥~40% каталога. <40% → «не указано» у
   большинства, фильтр бесполезен.
2. **Дискриминирующая сила** — значения разбросаны (нет одного значения на >~85%, нет «каждая уникальна»).
   Меряется по распределению из `_fields.json`.
3. **Релевантность решению** — два сигнала: (а) конкуренты выносят вперёд vs прячут в «ещё»; (б) входит
   ли в квиз (там ~6 слотов — дистиллят важного).
4. **Неизбыточность** — не дублирует другую ось (пятно ≈ площадь; «семья N человек» ≈ спальни).
5. **Стоимость UX** — ~6 Primary видимыми, остальное под «ещё фильтры». Диапазоны/бакеты, не гора чипов.

Вердикт: **Primary** (виден) / **Secondary** (под «ещё», для дотошных) / **Drop** (пусто/не разбрасывает/дубль).

## 1-bis. Верифицированные фильтр-сайдбары (сплошной headless-проход, 2026-07-05)

Проверено рендером всех трёх каталогов целиком (не выборка/ручной read — исправляет оговорку
`_fields.json _meta` про «partially re-derivable»). **Главный вывод: успешные конкуренты держат МАЛО
фильтров; раздутый список — только у legacy (наш старый сайт, 0 лидов).**

- **gwd (сильнейший) — 8 осей, ВСЕ количественные** (verbatim-блок «Все параметры фильтра», аудит): Тип
  проекта · Технология · Этажность · Площадь · Стоимость · Комнаты · Спальни · Санузлы. Сортировка (5-7 опций).
  **Нет стиля, особенностей, формы/крыши/пятна.**
- **aps — 4 оси:** Материал (брус/комбинир./камень/авторские) · Тип-этаж (1-эт/2-эт/популярные/бани) ·
  Стиль (8: классич./фахверк/плоская крыша/барн/райт/финский/hi-tech/европейский) · Площадь (до 200 /
  200-300 / от 300). **Нет фильтра цены и спален.**
- **legacy (0 лидов) — 7+ осей раздутых:** Размеры пятна (32 значения 7×8…15×15) · Площадь · Цена ·
  Этажность · Тип проживания · Особенности (21) · Стиль (14) + доп. категории. Это НЕ копируем.

**Итог:** 6 Primary — в одном классе с gwd (8 количественных осей) и намного меньше раздутого legacy.
«Мало фильтров» — не пробел, а осознанный паттерн успешных. gwd вообще фильтрует только по числам (без стиля/особенностей).

## 3. Итоговый UI фильтров

**Primary (видны сразу, ~6):** Технология/материал · Площадь · Цена · Этажность · Спальни · Стиль.
**Secondary (под «Ещё фильтры», для дотошных):** Санузлы · Назначение (ПМЖ/дачный) · Особенности
(терраса/гараж/балкон + редкие, когда наполнят) · [запас под будущие].
**Сортировка (отд. контрол):** рекомендованные · цена ↑↓ · площадь ↑↓ · по популярности («построен N раз»).
**Не заводим:** размер пятна, форма дома, тип крыши, редкие особенности (пока пусто), «семья/элитные» —
как фильтры (остаются SEO-подборками `ProjectSelection`).

## 4. Общий словарь критериев (питает фильтры И квиз)

`purpose(назначение)` · `area(площадь)` · `budget(бюджет=цена)` · `floors(этажность)` ·
`bedrooms(спальни)` · `material(технология)` · `style(стиль)` · `bathrooms` · `features[]`.
Каждый критерий — одна CMS-сущность (Taxonomy/поле). Фильтр = чип/диапазон по критерию; шаг квиза =
вопрос по критерию. Один источник — нет задвоения.

## 5. Квиз — спецификация

**Тип квиза — РЕШЕНО: подбор-гибрид** (владелец, 2026-07-05). Для контекста, что отвергнуто:
- **Смета-квиз** (как legacy 6 шагов: этажи/площадь/фундамент/крыша/бюджет/сроки) — оценивает стоимость
  СТРОЙКИ по конструктиву, каталог не использует. Для компаний БЕЗ каталога. **Не берём** — у нас есть каталог.

**Реализуем гибрид:** вопросы = критерии подбора (назначение/площадь/бюджет/этажность/спальни/материал-
стиль) → матчинг по каталогу → показать **3-5 подходящих проектов + вилку цены** (из
`ProjectMaterialVariant.priceFrom` подобранных) → захват лида (`source=quiz`). Это и «магнит» (вилка цены
даёт «ощущение сметы»), и реальные проекты, и ведёт в каталог; переиспользует словарь критериев (§4).
Конструктив (фундамент/крыша) НЕ спрашиваем — при готовом каталоге не нужен.

**Шаги (5-6, из словаря критериев):**
1. Назначение (ПМЖ / дача / сезонно) 2. Площадь (бакет) 3. Бюджет (бакет) 4. Этажность 5. Спальни
6. (опц.) Материал/стиль. → «Показать подходящие» + вилка цены + форма контакта.

**CMS-админимость (обязательно, §6.6):** квиз — не хардкод. Структура в CMS-сущности `Quiz`:
`steps[]{criterion(из словаря), label, options[]{label,value}, required}` + маппинг ответов на фильтр
каталога (matchesSelection). Редактор меняет вопросы/варианты/порядок/тексты **без кода и релизов**.
Матчинг ответов = тот же `SelectionFilter`, что у фильтров/подборок → один движок.
